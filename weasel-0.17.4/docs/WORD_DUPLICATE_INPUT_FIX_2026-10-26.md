# Word 重复输入：针对性修复与安装检查

日期：2026-10-26。代码提交 `61c3560`，基于 `98db7bb`；仅本地 main，未推送。

## 已修复的路径

Word 的查询 / 实际回调可取得不同 GetMessageTime。此前实际回调因此错过缓存，再次进入按键处理。本轮把“重复查询判断”与“实际回调确认”分开：

- 查询仍使用时间、上下文身份、键和完整消息标志识别重复查询；新时间的查询开启新一轮处理。
- 同方向实际回调以相同上下文、键和完整标志消费最近一次已处理查询的结果，不要求 GetMessageTime 相等；结果只消费一次。
- 保存原始 handled 结果，包括 false，防止宿主再次转交未处理或抬起事件时重复推进后端状态；不会把未处理改报为已处理。
- 抬起 / 按下事件退休相反方向的凭据，失焦 / 文档切换 / 编辑失效仍清理缓存；后续真实输入不能重复使用已消费凭据。

没有更改 Rime 的标点、候选学习或纠错 Tab 替换算法。

仍有协议边界：查询若被遗弃且没有任何抬起、焦点、中途按键或新查询，随后同参数 actual-only 事件无法仅靠这组回调判断是否为新物理键。本轮不为消除此歧义擅自添加会吞正常按键的全局时间窗口；已覆盖有明确事件边界的遗弃查询、实际回调独立到达、同键和自动重复场景，不宣称覆盖任意不完整宿主协议。

## 真实 Rime 对照与解析边界

新增 `BackendCheck.exe --word-key-contract`，仅在独立测试后端的新私有会话中发送编译的合成样例；“应用追加 ASCII”的部分由测试工具模拟，不操作真实 Word。双架构均得到：

| 送入后端的固定键串 | 提交与模拟应用文本 | 最终组合 |
| --- | --- | --- |
| nihao1. | 你好。 | 无 |
| nihao11.（故意重复选词数字） | 你好1 | 英文点号待确认 |
| 3.14 空格 | 3.14 空格 | 无 |

这验证了前轮推断的后端连锁机制：多余数字进入后端后，点号确实可能进入数字分隔符分支；无需破坏正常小数规则。它不单独证明每次 Word 原生字符插入的内部调用栈，需结合实机结果判断修复。

初次新测试读取 context 却不请求 config 时自身崩溃，定位到已有 `Configurator::Store` 检查 p_context 却解引用 p_config。已改为检查 p_config，并覆盖 config-only / context-only。另修正光标三坐标解析的长度检查，拒绝只有两项时访问第三项。正常完整响应保持原行为。

测试点号初次比较还发现软光标 U+2038；已依据真实 inline_preedit 配置区分“.”和“.‸”，没有无条件删除字符或放松任意候选校验。最终三组全部通过；早期失败日志保留，见 `word-receipt-rime-contract-*`，最终为 `word-receipt-rime-contract-verified-*`。

## Word 无提示的下一项阻断

固定阶段的新鲜 LastAutomatic 为 ScopeUnavailable，尚未进入模型 / 显示链路。最近范围详情为 GetValueFailed / E_FAIL；该详情结构本身没有时戳，不把它当成具独立时戳的完整接口对照。捕获计数仍有旧值，不能把它当作本轮成功捕获。

下一步应在 Word 的实际 TSF 范围上对照输入范围属性与可验证的本输入法上屏范围，查明无法确认的接口；保护状态不明确时继续拒绝自动纠错。不要通过取消私密 / 只读保护来强行显示提示，也不要再次按模型速度或 UI 位置猜测本轮阻断。

普通模式原反馈为“只出现‘你好’。手动输入‘你好1’，下一次句号是英文点号，符合逻辑”；不把该措辞扩写为逐字符记录。结合前一轮三项“全部正常”，确认本轮基础重复输入修复通过两种运行方式的人工检查。
