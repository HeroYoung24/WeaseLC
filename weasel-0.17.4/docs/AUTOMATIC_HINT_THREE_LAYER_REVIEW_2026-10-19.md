# 自动提示缺失：三个角度的重新审查（2026-10-19）

## 结论与此前排查的不足

本轮重新审查上文捕获、模型链路、提示与 Tab，并补做包环境的只读复现。**已复现一个足以让纠错关闭的部署兼容缺陷：普通用户环境能读到开启设置，实际记事本所用的 MSIX 包环境读不到同一个设置。** 默认关闭及诊断写入逻辑，会进一步造成“没有提示、外部入口记录全空”的组合症状。

这已成为第一修复目标。尚未将共享配置修复部署到实际记事本，不能宣称所有提示/Tab 问题均已解决，也不能排除后续候选窗口或焦点阻断。

此前的不足是：独立工作进程和模拟宿主的通过结果，被用于推进反复实机测试，但没有先验证宿主配置视图与外部控制程序一致。DLL 加载、普通用户 ACL 和中等完整性，均不能替代这项验证；“外部没有日志”也不能证明回调没有执行。

## 2. 角度一：是否确实读入、记录和处理了上文

### 代码路径和实际边界

`_HandleKey → _UpdateComposition → CServerResponseEditSession → _ApplyServerResponse → _ApplyCompositionResponse → Capture → Validate/ReadExact`。

Capture 位于中文提交、结束组合和生命周期核对之后。它只累计同一文档相邻、本输入法新上屏的片段，最多 1024 UTF-16 单元，最近一次提交约 10 秒后过期。已有文档任意历史没有进入自动模型请求，探测菜单只保存读取状态与长度。因此“能够输入中文”“菜单探测有结果”不能证明自动上文已送模型。

### 当前第一阻断

`CorrectionPreferences.cpp::ReadPreferences` 查询失败时返回默认 Preferences；默认 mode=Off、automatic.enabled=false。`AutomaticCorrection.cpp::Capture` 读取后会直接返回，尚未进入 `Report(Captured)`、`Validate/ReadExact`、工作进程或显示。

据已复现的包环境结果，现有代码在该环境无法获得控制程序设置的开启状态。这是直接可解释当前缺失的配置缺陷；此前“可能没有捕获到上文”的定位过于粗糙。

入口记录同样依赖宿主自己的 HKCU。`SaveFrontendDiagnostic` 仅打开已存在子键，打开失败即返回；写入返回值也未报告。包环境找不到子键时，LastKey/LastCommit/LastGate 都不会出现，即使相应函数曾执行。故不能再从这些记录缺失推断输入事件缺失。

### 其他已查情况

- “无建议后丢失上文”和显式 IS_DEFAULT 被拒绝已分别修复，有独立回归；它们不代表此次真实链路已通过。
- 提交范围 GetRange 的失败结果当前没有完整传播到纠错诊断；它也是需要保留明确错误的早退点。
- 高频词由 Rime 原生用户词典学习，不直接成为纠错白名单；本次没有发现“频率高自动压制建议”的实现。

## 3. 角度二：模型是否接入异常、太慢、未收到文字

### 已验证与未验证

已安装工作进程在普通环境接收编译句后立即返回建议；此次没有 HTTP 请求，记录中的 200 是固定传输夹具的状态。此前真实本地 Qwen 在独立宿主的合成测试通过，单次日志约 1.3 秒；这不能证明真实记事本已经发送请求。

当前没有可信证据证明记事本前端已发出模型请求。配置关闭可以在请求前终止。`/correction-worker` 又独立读取 HKCU 的设置、固定响应标志及保留词；只修前端的开关，仍可能留下工作进程环境不一致的问题。真实子进程的包继承行为须单独核对，不能套用独立启动的健康检查结果。

### 已确认的两项代码问题

1. **超时预算不一致。** 模型配置允许 2–60 秒，常用设置为 30 秒；自动状态从上屏起约 10 秒即取消，包含防抖/启动/推理时间。慢于剩余有效期的响应必然无法展示。这不是此次即时固定响应缺失的解释，但会影响真实模型。
2. **协议压平错误。** AutomaticReply 只有 count/items，没有模型状态或错误字段。配置不满足、HTTP 错误、超时、解析失败等可能最终输出合法零条建议；前端将其当作“没有可展示建议”，无法区分模型确实无错、阈值/保留词过滤与调用失败。外部 LastWorker 还受到当前注册表视图问题影响。

修复应让结果协议明确携带状态、请求标识、错误与耗时，并使请求预算与建议有效期一致；模型故障不应被记为正常的无建议结论。

## 4. 角度三：提示框和 Tab 是否被逻辑挡住

### 显示的实际条件

`AcceptReply` 验证原文、偏移和分数后仅设置 ready；显示还要求：有效光标位置、宿主在前台、满足下一次组合输入时机、建议未过期、候选位置可获取、布局能放入工作区。Tab 仅在提示窗口可见且文档再次验证通过时接管按键。

所以没有提示时，Tab 按键本身不一定有故障；前端可能根本没有可接受的建议，或提示在显示门控处被隐藏。

### 已确认的兼容限制与观测缺陷

- `CandidateList::WindowRect` 要求 `_pbShow` 且本项目的候选窗口真实存在。宿主通过 BeginUIElement 接管候选 UI 时 `_pbShow=false`，正式 Refresh 会报告 CandidateUnavailable 并隐藏提示。该条件是否在本次记事本实际触发尚未证实，应在配置修复后检查。
- 探测构建的 `testing_` 分支绕过真实配置读取/设置版本核对、真实焦点核对，还可绕过候选窗口位置不足。这解释了为什么 188 项模拟回归不能证明真实宿主显示已通过。
- Refresh 在 `SetWindowPos` 之前报告 Shown，且未检查该调用返回值。诊断中的 Shown 目前也不能严格证明窗口实际显示。
- SetTimer 失败没有明确报告，可能让已捕获状态不再推进到工作进程；需要纳入失败状态。

此前固定传输夹具仍依赖前端读到设置并通过范围校验，并非“无需任何前置条件必然弹窗”的测试。本轮半角/全角句号及无句号边界已修复，但它无法绕过本次配置缺失。

## 5. 修复顺序和验收门槛

| 优先级 | 工作 | 完成证据 |
| --- | --- | --- |
| P0 | 将共享配置、版本及诊断从宿主 HKCU 解耦 | 普通与记事本包环境获得同一配置版本和开启状态，控制程序能收到同一请求的阶段记录 |
| P0 | 通过普通用户、非包环境控制进程协调推理 | 实际工作进程身份及配置来源已确认；请求/结果以有界、同用户认证 IPC 关联 |
| P1 | 模型结果协议区分无建议/过滤/传输失败/超时/解析错误 | 每个故障注入返回明确状态，不压成零条成功响应 |
| P1 | 对齐推理预算与建议有效期 | 慢/取消/过期用例行为明确，旧请求不修改新文档 |
| P1 | 真正验证候选锚点与显示结果 | 正式分支记录 ready、候选归属、位置和实际显示成功；宿主接管 UI 有明确降级策略 |
| P1 | 提示出现后验证 Tab、拼音保留及鼠标中断 | 实际记事本改正前文、保留 ni，输入/退格正常；无提示时 Tab 继续交给宿主 |

优先复用已有独立后端/控制进程及会话门控：由非包进程维护单一配置、保留词和版本，向 TSF 传递必要的有界快照；推理继续异步，不阻塞 Rime 按键。诊断同样发往控制进程，不要求每个宿主写同一个 HKCU。具体接口仍需实现和验证；本轮没有完成这一架构修复。

保持配置读取失败默认关闭、敏感字段拒绝和原文/光标核对。默认开启或放宽安全门控均不能作为配置兼容修复。

下一次人工实测前，先在普通环境和记事本包环境完成配置/诊断一致性、固定请求、状态协议与显示门控的定向验证。人工只需验收实际候选提示与 Tab，而不是继续反复试相同错句找日志。

## 6. 本轮状态

本轮仅新增只读复现工具及分析文档，没有更换 DLL 或修改记事本包/系统权限。独立测试版仍安装，专用后端保留；复现结束后已关闭普通视图的自动纠错。真实模型未启动。先前 Purge 的“设置已清理”仅验证普通视图，不应推广为所有 MSIX 私有视图；本轮查询的记事本项目设置为缺失，不能据此承诺其他宿主均无私有副本。

收尾只读核对：原版输入法 DLL 哈希及安装注册信息与测试前基线一致，18963 端口无模型监听，普通设置视图确认为 mode=Off、automatic.enabled=false。核对保存在 `output/LocalTest/entry-final-analysis-state-2026-10-19.json` 与 `entry-final-normal-review-2026-10-19.json`。
